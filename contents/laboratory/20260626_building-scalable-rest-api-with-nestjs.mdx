> "A backend does not become hard when traffic grows. It becomes hard when every module can reach every variable."

This experiment set out to answer one question: how far can a modular [NestJS](https://nestjs.com) service grow before its architecture stops helping and starts hurting? The result is a REST API that now serves three frontend applications — a web dashboard, a mobile client, and a public integrations surface — from a single deployable with cleanly separated internal modules.

## Module Layout

The service is organized as a modular monolith. Each module owns its routes, services, DTOs, and persistence, and exposes one narrow public interface:

```text
src/
  auth/        # login, JWT issue/refresh, guards
  users/       # accounts, profiles
  products/    # catalog read/write
  orders/      # ordering + payment integration
  shared/      # Prisma client, config, interceptors
  app.module.ts
```

The boundary rule is mechanical: modules may only import from another module's `index.ts`. Everything else — internal services, entities, repositories — is private. NestJS module deps plus an ESLint boundary rule enforce both.

```typescript
// modules/orders/index.ts — the entire public surface of orders
export { OrdersService } from "./orders.service";
export { CreateOrderDto } from "./dto/create-order.dto";
export type { OrderView } from "./views/order.view";
```

## Authentication and Authorization

Auth is JWT-based with short-lived access tokens and rotating refresh tokens. The interesting part is the authorization layer: role-based at the route level, ownership checks at the service level, both expressed as guards so no handler forgets them.

```typescript
@UseGuards(JwtAuthGuard, RolesGuard)
@Roles("admin", "owner")
@Post(":id/checkout")
async checkout(@Param("id") id: string, @RequestUser() user: RequestUser) {
    // service performs its own ownership check below this line
    return this.orders.checkout(id, user.id);
}
```

> [!WARNING]
> Route-level roles are necessary but not sufficient. Any handler that reads user-scoped data must re-check ownership against the authenticated subject — delegating those checks to the frontend or trusting the route guard is how IDOR bugs are born.

## Validation at the Boundary

Every incoming request passes through class-validator DTOs, and every outgoing response passes through an explicit view mapping. Nothing leaks a persistence entity to a serializer by accident:

```typescript
export class CreateOrderDto {
    @IsUUID() productId!: string;
    @IsInt() @Min(1) @Max(50) quantity!: number;
    @IsOptional() @IsString() @MaxLength(280) note?: string;
}
```

With [Prisma](https://www.prisma.io) behind it, the translation layer between HTTP and the database is small, typed, and explicit.

## Database Abstraction That Earns Its Keep

Repositories are interfaces implemented once, with Prisma. That sounds like ceremony for its own sake; it paid for itself exactly once, when a reporting endpoint needed a read-model query the Prisma API couldn't express cleanly — the repository got a raw-SQL implementation, and no module outside noticed.

```typescript
export interface OrderRepository {
    findOpenForUser(userId: string): Promise<Order[]>;
    countPerDaySince(day: Date): Promise<{ day: string; count: number }[]>;
}
```

## Deployment with Docker

One container, one config surface, twelve environment variables — all validated at boot with a typed config module. Database migrations run as a separate one-off job before the app deploy; the app itself never mutates schema.

```yaml
healthcheck:
    test: ["CMD", "wget", "-qO-", "http://localhost:3000/healthz"]
    interval: 30s
    timeout: 3s
    retries: 3
```

## What the Experiment Proved

- A modular monolith carried ~4x the initial traffic with zero structural changes; the boundary rule made hot paths diagnosable in minutes
- The one-RestController-per-module convention kept reviewable pull requests small even as the service grew from 9 to 34 routes
- The layer the project almost skipped — explicit view mapping — prevented the leakiest class of bugs: entities drifting into public responses

The service remains a single deployment. If a module ever needs independent scaling, the repository interface is the seam — but nothing so far has needed it.

> "Scaling is usually a symptom. In this case it was mostly a compiler-enforced module map doing the work."
