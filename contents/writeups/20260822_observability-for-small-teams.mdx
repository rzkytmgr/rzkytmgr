> “You do not need a bigger dashboard. You need better questions.”

Observability vendors would love you to believe you need a platform, an agent, and a data lake before you can understand your system. Small teams need the opposite: the smallest set of tools that can answer “what is broken, and why?”

## Structured Logs First

If you only adopt one practice, make it structured logs. A JSON log line is machine-parseable, filterable, and greppable — which is everything a text log is not.

```json
{
    "level": "error",
    "msg": "payment provider timeout",
    "service": "checkout",
    "order_id": "ord_9921",
    "provider": "stripe",
    "retries": 2,
    "duration_ms": 3400
}
```

The rule is simple: **searchable fields, not sentences**. Every log line that might be queried later gets a field now.

## One Correlation ID Per Request

The single highest-leverage observability change is a correlation ID. Pass it through every service, log line, and error report. When something fails, you can pull the entire journey of one request out of the logs.

```typescript
export function requestContext(req: Request) {
    return {
        traceId: req.headers.get("x-trace-id") ?? randomUUID(),
        service: SERVICE_NAME,
    };
}
```

> [!TIP]
> Start every outbound HTTP call with the same header. Distributed tracing will eventually replace this — but the header survives the migration.

## Metrics: Measure What Decides Capacity

Metrics answer “is this trending toward a problem?” Keep the list short and tied to decisions:

| Metric                      | The decision it informs            |
| --------------------------- | ---------------------------------- |
| Request rate and error rate | “Is the deploy safe to roll back?” |
| p50/p95/p99 latency         | “Are users feeling the slowdown?”  |
| Queue depth                 | “Do we need to scale workers?”     |
| Database saturation         | “Is the bottleneck the storage?”   |

A dashboard with twelve charts and no questions is wallpaper. Design around one question per view.

## Alert on Symptoms, Not Causes

Alerts are most useful when they describe what users experience, and least useful when they describe the mechanism you already guessed:

- **Good alert:** “Checkout error rate above 1% for 5 minutes”
- **Bad alert:** “Redis connection pool at 80%” (the cause, not the symptom)

```yaml
groups:
    - name: checkout
      rules:
          - alert: CheckoutErrorRateHigh
            expr: rate(checkout_errors_total[5m]) > 0.01
            for: 5m
            labels:
                severity: page
```

> [!WARNING]
> Every page-level alert should come with a runbook. An alert without a runbook is just noise with a higher volume knob.

## Conclusion

Small teams do not need an observability platform. They need:

- Structured logs with searchable fields
- A correlation ID on every request
- A handful of metrics tied to capacity decisions
- Alerts on symptoms, with runbooks

> “Debugging is the process of reconstructing a story from evidence. Observability is making sure the evidence exists.”

Start with the correlation ID and structured logs. By the time you grow into more tooling, the evidence will be there waiting.
