## Starting with the Problem

A system does not become complex simply because it contains many lines of code. Complexity emerges when a small change requires understanding too many parts of the system.

For example, an application may initially contain:

- One backend application
- One database
- One deployment process
- One engineering team

Over time, new requirements appear:

1. The number of users increases
2. Traffic becomes unpredictable
3. New features must be released faster
4. Multiple business domains begin evolving independently

At this point a team may consider:

- Splitting the application into multiple services
- Adding a message broker
- Introducing a distributed cache
- Separating databases by business domain

However, these decisions are not automatically correct. Adding a new technology may solve one problem while introducing several new operational problems.

### Core Principles

A few useful principles are:

1. **Understand the problem before choosing a technology.**
2. **Measure bottlenecks before optimizing.**
3. **Introduce complexity gradually.**
4. **Make sure the team can support the operational cost.**

## Code Block: JavaScript

```javascript
/**
 * Calculates the total price of all items.
 *
 * @param {Array<{price: number, quantity: number}>} items
 * @returns {number}
 */
function calculateTotal(items) {
    return items.reduce((total, item) => {
        return total + item.price * item.quantity;
    }, 0);
}

const items = [
    { price: 15000, quantity: 2 },
    { price: 25000, quantity: 1 },
];

console.log(calculateTotal(items));
// Output: 55000
```

## Trade-offs to Consider

| Decision                  | Benefits                                | Costs                                                |
| ------------------------- | --------------------------------------- | ---------------------------------------------------- |
| Modular Monolith          | Simple deployment and local development | Requires discipline to preserve module boundaries    |
| Microservices             | Independent deployment and scaling      | Higher operational and distributed-system complexity |
| Shared Database           | Simple data access and transactions     | Strong coupling between services                     |
| Database per Service      | Clear data ownership                    | More difficult cross-service queries                 |
| Synchronous Communication | Easy request-response model             | Strong runtime dependency                            |
| Asynchronous Messaging    | Better decoupling and resilience        | Eventual consistency and debugging complexity        |

The correct choice depends on the actual constraints of the product, team, infrastructure, and business domain.

## Example of Longer Content

A system that is easy to extend is not merely a system with clean code. It should also have clear boundaries, predictable deployment processes, sufficient observability, and enough documentation to help engineers understand the reasoning behind important decisions.

When a change is made, an engineer should be able to estimate which parts of the system might be affected. If a small change requires understanding the entire repository, the system may have excessive coupling or poorly defined module boundaries.

In practice, no architecture is perfect. Every decision has a cost. Microservices may provide independent deployment and team autonomy, but they also introduce network complexity, observability requirements, distributed data consistency concerns, and additional operational overhead.

A monolith is often easier to build and operate at the beginning. However, it can become difficult to evolve if domain boundaries are ignored and unrelated responsibilities become tightly coupled.

## Conclusion

A good system is not a system that uses the largest number of technologies.

A good system is one that:

- Can be understood by the team
- Can be changed safely
- Has clear boundaries
- Meets current requirements
- Has a reasonable path for future evolution
- Does not introduce complexity without a clear benefit

> “Simplicity is not the absence of complexity, but the careful management of it.”
