> “An API is a contract. Every breaking change is a bill you send to someone else’s code.”

Every public API eventually needs to change. The real question is not _whether_ it will change, but whether the change can be shipped without forcing every consumer to coordinate with you at the same time.

This article collects the practices that keep API evolution boring: additive changes first, compatibility rules that are actually enforced, and a deprecation process that gives consumers a real migration path.

## Why APIs Break

Breaking changes rarely happen because someone wanted to be destructive. They usually slip in through one of these doors:

- **Renaming** a field or endpoint because the old name aged poorly
- **Changing types** — a string becomes an object, an integer becomes a float
- **Tightening validation** — values that used to pass now fail
- **Reordering or removing** default behavior that consumers quietly depended on

The last one is the most dangerous, because it is invisible. Your tests pass, the response looks fine, and only one customer notices that their pagination loop now spins forever.

## Prefer Additive Changes

The cheapest way to evolve an API is to add to it. Adding a new field, a new endpoint, or a new query parameter does not break existing consumers.

```json
{
    "id": "usr_9281",
    "name": "Aulia",
    "email": "aulia@example.com",
    "created_at": "2024-11-02T09:14:00Z"
}
```

If you need to change the meaning of `name`, do not mutate it — add `display_name` and deprecate the old field. Both can coexist for a full deprecation cycle.

### The Rules of Backward Compatibility

A short checklist to run before merging any API change:

- [x] Adding a field to a response — safe
- [x] Adding an optional request parameter — safe
- [ ] Removing a field from a response — breaking
- [ ] Changing an existing field’s type — breaking
- [ ] Changing error semantics — breaking, even if the shape stays the same
- [ ] Tightening validation rules — breaking

## Versioning Is a Last Resort

Versioning is the most visible solution and often the most expensive one. Every version you support is a codebase you have to maintain and a mental model your consumers have to carry.

| Strategy            | When it works                          | When it hurts                       |
| ------------------- | -------------------------------------- | ----------------------------------- |
| URL versioning      | Long-lived public APIs                 | Every consumer must migrate in sync |
| Header versioning   | Clean URLs, flexible negotiation       | Hidden from casual inspection       |
| Content negotiation | Media-type-driven APIs                 | More client complexity              |
| No versioning       | Internal APIs with additive discipline | Hard to escape once consumers grow  |

> [!NOTE]
> Version numbers are a promise you have to keep. Shipping `v2` does not end `v1` — it doubles your maintenance surface until every consumer migrates.

## Deprecation Is a Process, Not an Event

A deprecation announcement without a timeline is a rumor. A good deprecation has four parts:

1. **Communication** — document it and announce it with a date
2. **Signaling** — `Sunset` and `Deprecation` headers so clients can react programmatically
3. **Grace period** — long enough for consumers to migrate at their own pace
4. **Hard removal** — only after the usage metrics say the old path is quiet

```http
HTTP/1.1 200 OK
Deprecation: true
Sunset: Sat, 01 Mar 2025 00:00:00 GMT
Link: <https://api.example.com/v2/users>; rel="successor-version"
```

## Contract Testing Closes the Loop

Design rules help, but rules are only as strong as the tests that enforce them. A contract test suite that runs against every release catches accidental breaks before consumers do.

```typescript
test("new response fields must be additive", async () => {
    const schema = await getSchema("/users");
    const previous = await getSchema("/users", { version: "2024-06" });

    for (const key of Object.keys(previous.properties)) {
        expect(schema.properties).toHaveProperty(key);
    }
});
```

When a contract test fails, the release is blocked until someone either reverts the change or starts the formal deprecation process.

## Conclusion

Evolving an API without breaking consumers is mostly a matter of discipline:

- Add before you modify
- Enforce compatibility with tests, not intentions
- Treat versioning as a cost center, not a badge
- Give deprecations a real timeline with programmatic signals

> “The best API version is the one your consumers never have to think about.”

Your consumers will not thank you for a flawless migration — but they will never forgive a silent break.
